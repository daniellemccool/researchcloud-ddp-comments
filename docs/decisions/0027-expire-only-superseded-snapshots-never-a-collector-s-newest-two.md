# Expire only superseded snapshots, never a collector's newest two

## Decision

Per creator and type, the desk marks a snapshot to expire only when it is outside the newest two, a newer one has at least as many rows, and it borders no drop in rows. It never changes `keep` or a foreign expiry, never marks a kept snapshot or re-marks its own, and unmarks one that is kept or protected.

## Guidance

- The desk decides and 4CAT deletes: a mark adds the two parameters `expires-after = now + 604800` and `desk-retention = true` to the dataset's `parameters` and re-serialises that text through jsonb (key order and spacing can change; 4CAT reads it with `json.loads`), and 4CAT's expire worker does the deleting. The retention pass never deletes a dataset, its rows or its files itself.
- A snapshot is a dataset of type `tiktok-search` or `tiktok-comments-search` with `key_parent = ''`, finished, `num_rows > 0` and not a standalone copy (next bullet), grouped by `creator` and ordered by `timestamp` descending (ties by key). It is superseded only if a newer one in its group has `num_rows ≥` its own. It borders a drop when it is before one (its next-newer snapshot has fewer rows) or after one (its next-older snapshot has more); next-newer and next-older are taken over every snapshot in the group, whatever its flags, and equal rows are no drop. The newest two, one no newer snapshot supersedes, and one that borders a drop are kept.
- Every standalone copy is excluded: a merge, filter or refresh output takes the input's type and is top-level, and its creator may be a collector, so the read and `MarkExpiring`'s guard refuse any dataset whose `parameters` carry `copied_from` or `producer_type`, whatever their values; a Zeeschuimer import has neither. Processor outputs and every other type are never touched. A merge job started from a snapshot that expires goes with it as its child; the detached standalone survives.
- The grace period is 7 days (604800 s) and the pass runs at desk start, then every 15 minutes, or 10 minutes after a failed pass; each 4CAT call in a pass has its own one-minute deadline, so a blocked psql fails only that call; all four are constants in one place. The runner, its switch and its status live in `internal/retention/runner.go`; `cmd/desk/main.go` only builds the switch's path and starts it.
- The switch: the pass marks and unmarks only while `<desk root>/state/retention-on` exists, looked at at the start of every pass (`Runner.Enabled`; nil, false or any stat error is a dry run). Without it the pass is a dry run that reads and decides but writes nothing, logs what it would mark and unmark when that changes, and says "(dry run)" on the admin line. v1.2.0 ships without the file. Switched off, the desk does not unmark either: existing marks stay until removed by hand (`docs/release.md`).
- A snapshot is desk-marked when it carries `desk-retention = true` and an `expires-after`. A desk-marked snapshot is never marked again, so its expiry stays at the first mark + 7 days; one the rule now keeps (an admin deleted newer snapshots, or it now borders a drop) is unmarked by removing both `expires-after` and `desk-retention`. A marker without an `expires-after` is stale (4CAT's keep route deletes the expiry and leaves the marker): such a row is an ordinary snapshot and may be marked afresh.
- The desk never changes `keep`, never marks a kept snapshot, and never changes a snapshot with an `expires-after` but no `desk-retention`. It does take its own mark off a kept snapshot, superseded or not: 4CAT's bulk "keep" leaves the expiry in place and "unkeep" removes only `keep`, so otherwise an unkeep after the expiry date gets the snapshot deleted within 30 minutes. `MarkExpiring`'s UPDATE itself skips a row that has `keep` or already has `expires-after`, so an admin's `keep` or expiry set between the desk's read and its write is never overwritten. A deletion of newer snapshots in that time is repaired by the next pass, which normally runs before 4CAT's 30-minute worker; that narrows the window and does not close it.
- The Data sources expiry timeouts for the TikTok types stay 0; only `expires-after` drives deletion, because a source timeout would delete a quiet collector's only snapshots. This is an operator setting that no code asserts; `docs/release.md` carries the check.
- A pass that cannot read 4CAT or psql logs one line and changes nothing; the next pass retries. A failed mark does not stop the unmark, the protective half; either write failing makes the pass failed. Logs carry dataset keys, creators, types, counts and times, plus the 4CAT client's error text on a failed call (status codes and fixed strings today): one line per mark or unmark, and a summary only when a pass changed something. In a real pass the counts and those lines come from the keys the writes return, never from what was asked; in a dry run, which writes nothing, they are `Decide`'s lists.
- Enforced by `TestNewestTwoKept`, `TestPreDropKept`, `TestEqualRowsSupersede`, `TestDropBothSidesKept`, `TestDropSurvivesCleanup`, `TestEqualRowsIsNoDrop`, `TestConsecutiveDrops`, `TestMarkedSnapshotBesideDropIsUnmarked`, `TestForeignExpiryUntouched`, `TestForeignExpiryStillCounts`, `TestMergeOutputsIgnored`, `TestUnmarkWhenNoLongerSuperseded`, `TestAlreadyMarkedNotRemarked`, `TestKeptAndMarkedIsUnmarked`, `TestKeptStillCounts`, `TestGroupsByCreatorAndType`, `TestTimestampTieByKey`, `TestPassCallsInOrder`, `TestPassLogLines`, `TestRetentionSurvivesReadFailure`, `TestUnmarkAfterFailedMark`, `TestFailedUnmarkFailsPass`, `TestCountsFromReturnedKeys`, `TestEmptyListsMakeNoCall`, `TestSummaryOnlyWhenChanged`, `TestNextPass`, `TestRunStopsOnCancel`, `TestStatusDuringPass`, `TestStatusLine`, `TestDryRunWritesNothing`, `TestNilEnabledIsDryRun`, `TestSwitchReadEveryPass`, `TestDryRunLines`, `TestDryRunReadFailure`, `TestStoreCallDeadlines`, `TestUnmarkAfterMarkTimeout`, `TestReadTimeoutFails` (`internal/retention`); `TestCopiesExcluded`, `TestSnapshotsGuards`, `TestMarkExpiringGuard`, `TestUnmarkGuard`, `TestBadInputRunsNoSQL`, `TestStaleMarker` (`internal/fourcat`); `TestAdminOverviewShowsRetentionLine` (`internal/web`).

## Why

Every Zeeschuimer upload holds the collector's whole collection so far, so older uploads are redundant copies and 4CAT's storage grows with uploads × size. The row test alone only delays the loss of a pre-reset collection, because a later collection that grows as large holds different items, so the rule keeps both sides of every drop; and no row-count rule sees a reset followed by more collecting before the next upload, so collectors must never press Reset. Weakening the drop rule, the foreign-expiry guard, the no-re-mark rule or the switch would delete a collector's only copy, override an admin, push an expiry forward for ever, or write before the operator has checked a dry run.
